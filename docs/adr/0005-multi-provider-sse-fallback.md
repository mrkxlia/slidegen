# 0005. マルチプロバイダ LLM 抽象 ＋ SSE 専用 ＋ 2層フォールバック

- ステータス: 採用 (Accepted)
- 日付: 2026-06-28
- 関連: `gateway/src/providers.ts`, `gateway/src/stream.ts`, `gateway/src/index.ts`, `frontend/src/App.tsx`

## コンテキスト

- 無料 LLM 枠は**不安定**（レート上限・一時エラー）で、**モデルの入れ替わりも激しい**（IDやシャットダウン）。
- Cloudflare Worker は**非同期 fetch のみ**許可（同期 SDK 不可）。
- 壁打ち/生成は**長文**になりがちで、待ち時間が UX を損なう。
- 劣化モデル（Gemma 等）は HTTP 200 を返しつつ**「DSL として無効」な出力**（`}` の連発等）をすることがある。

## 決定

1. **プロバイダ横断の抽象**（`providers.ts`）。`gemini`/`openrouter`/`workers_ai`/`openai`/`anthropic` を全て fetch で実装。
   - **SSRF 不変条件**: エンドポイント URL はファイル内に固定。フロントからは provider(列挙)/model/system/messages のみ受ける（URL/base_url を受けない）。
   - `stream.ts` が各社の SSE/チャンクを**テキスト delta の AsyncGenerator** に正規化。`systemInstruction` 非対応モデルは system を先頭 user に畳む。
2. **`/api/chat` は SSE 専用**（非ストリームは廃止）。逐次表示で待ち時間を体感的に短縮し、長文の途中状態も扱える。
3. **2層のフォールバック（責務が異なるため統合しない）**:
   - **gateway `fallbackChain`**（`providers.ts`/`index.ts`）= **transport/provider エラー**（429/5xx/404 等）時に、同 tier の別モデルへ順に切替。途中出力があれば**部分出力を引き継いで継続**。
   - **frontend `dslFallbackModel`**（`App.tsx`）= **HTTP 200 だが DSL として無効**という**意味的失敗**時に、信頼できる別モデルで 1 回だけ再生成。
   - 前者は「通信/上流の失敗」、後者は「中身の妥当性」を検出する**別レイヤー**であり、片方では代替できない。

## 結果

良い点:

- 無料枠の不安定さ・モデル劣化があっても、壁打ち/生成が**途切れにくい**。
- SSE で UX が安定。SSRF 不変条件で鍵・到達先を保護。
- プロバイダ追加は catalog への 1 行追加で済む。

トレードオフ・注意:

- **モデルカタログがコードにハードコード**（ID・シャットダウン日）で**陳腐化しやすい** → 課題として [docs/backlog.md](../backlog.md) で管理。
- SSE 専用ゆえ、**全プロバイダのストリーム形式を正規化**する責務を `stream.ts` が負う。
- フォールバックが 2 箇所にあるため、**責務分界をドキュメント化**しておく必要がある（本 ADR がそれ）。

## 検討した代替案

- **単一プロバイダ**: 無料枠の不安定さに弱い。却下。
- **非ストリーム（一括応答）**: 壁打ちの体感が悪く、長文が打ち切られやすい。却下。
- **フォールバックを 1 層に統合**: 「通信失敗」と「中身が無効」は検出層が異なり、統合すると取りこぼす。却下。
