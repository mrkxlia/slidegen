# AI主導 スライド生成システム 設計ドキュメント

> **目的**: 会社のpotxテンプレートを土台に、AIにコンテンツ（記法/DSL）だけを書かせ、
> 「型カタログ」と「デザイン制約」で構造と見せ方を固定することで、
> 安定して・速く・修正可能な形でスライドを生成する仕組みを設計する。
>
> 本ドキュメントは、後でAIへのシステムプロンプト（「魂」）や Claude Code への指示の
> 原本として使うことを想定している。
>
> 用途: **社内報告・提案資料** および **技術資料**

---

## 0. 背景思想：中間記法パターン（MNP）

このシステムは、中間記法パターン（Mid Notation Pattern / MNP）の考え方を土台にしている。

MNPの要旨は「**AIにGUI（座標）を直接操作させるのではなく、GUIと同等のデータを持つ
内部処理用のDSLを設計し、それをAIに操作させる**」というもの。
Mermaidがテキストで図を安定生成できるのと同じ原理を、自前の領域に持ち込む。

MNPの基本4要素を本システムに当てはめると:

| MNPの要素 | 本システムでの対応 |
|---|---|
| DSL（記法） | スライドの内容を表す独自記法（report系）＋ Mermaid（技術系） |
| パーサー | 記法 → pptx（python-pptx）への変換器 |
| シリアライザー | （将来）編集結果 → 記法への逆変換 |
| システムプロンプト | デザイン制約＋型カタログ＝「魂」 |

---

## 1. 解こうとしている問題

AI（Claude/ChatGPT/Gemini等）に直接スライドを作らせると、以下が起きる。

### 1-1. レイアウト崩れ
- 要素がはみ出す・重なる（テキスト量に箱が追従しない）
- 整列・余白がバラバラ（基準線が揃わない）
- 1枚に詰め込みすぎ（情報の優先順位がつけられない）
- potxの書式（フォント・配色・プレースホルダー）を無視する

### 1-2. 構造・論理が弱い
- メッセージ（見出し）とボディ（中身）が噛み合わない
- 同じ用途でも毎回違う型で出る（一貫性がない）
- 資料全体のストーリーライン（課題→原因→施策→効果）が設計できない

### 1-3. 修正・運用が効かない
- 部分修正ができない（一部だけ直したいのに全体が作り直される）
- 再現性がない（同じ指示でも毎回違う）
- 編集可能な形で出てこない（画像出力だと手直しできない）

### 1-4. デザインがチグハグ（「よくわからないデザイン」になる）
- 装飾過多／意味のない装飾（影・グラデ・謎の囲み）
- 色を使いすぎ／配色に意図がない
- 視線の導線が設計されていない（均等配置で読む順序が消える）
- 余白が怖くて全部埋める
- フォント・サイズの階層がない

### 根本原因
ひとつに集約される。**AIに「座標・サイズ・整列」という空間的世界を直接操作させているから**、
かつ **AIは「視覚的な良し悪しの判断軸」を持たないため、足し算しかできず引き算（削ぎ落とし）ができないから**。
論理（何を言うか）と表現（どう配置するか）を同時に背負わせると両方が崩れる。

---

## 2. 解の方針：責任分界を引き直す（3層 + 1）

「AIに任せる領域」と「システム/人間が固定する領域」を分離する。

```
┌─────────────────────────────────────────────┐
│ AIが書く        → コンテンツ（記法 / DSL）       │  ← ここだけAIの仕事
├─────────────────────────────────────────────┤
│ 型カタログが固定 → 構造（どう配置するか）          │
│ デザイン制約が固定 → 見せ方（何をやってはいけないか）│  ← 全型に横断でかかる
│ potxが固定      → ブランド書式（フォント/配色）   │
└─────────────────────────────────────────────┘
   技術図は Mermaid を中間表現としてそのまま流用
```

- **型カタログ** = 「どう配置するか」（レイアウトの引き出し）
- **デザイン制約** = 「どう見せるか／何をやってはいけないか」（全型横断ルール）
- この両方を合わせたものが、AIに渡す **システムプロンプト＝「魂」** になる。

---

## 2-bis. 必達要件：生成されたpptxはPowerPointで編集可能であること

**最終成果物は、PowerPointで開いてテキスト・図形・色を自由に編集できる
ネイティブな .pptx でなければならない。** これは手段の選択を根本から規定する。

### 採用しない手段
- 画像出力（AIに絵を描かせる／HTMLを画像化する等）→ 1枚絵になり一切編集できない。**却下**。

### 採用する手段
- **python-pptx でネイティブ要素を組み立てる**。各要素は本物のPowerPointオブジェクトになる。

### パーサーが守るべき編集可能性ルール
1. **テキストは必ずテキストフレームに入れる**（画像化・アウトライン化しない。後から打ち直せる）
2. **可能な限り potx のプレースホルダーに流し込む**（レイアウト機能・アウトライン表示で編集でき、テーマ変更に追従）
3. **色・フォントはテーマ参照で指定**（直値ハードコードを避ける。テーマ配色を変えると全スライド追従＝デザイン制約も維持）
4. **図形はネイティブシェイプで作る**（箱は Rectangle、罫線は Line。グループ化で選択・移動しやすく）
5. **表は本物のPowerPointテーブル（add_table）で作る**（行・列の追加がPowerPoint上で可能）

> 原則: 「**AIが書くのは記法。パーサーは記法を、PowerPointが理解できる
> ネイティブ要素に翻訳する。画像には絶対にしない。**」

## 3. デザイン制約（「魂」の中核 / 全型横断）

3つの独立ソース（資料作成メソッド画像群・Web上のコンサル流解説・「鉄則8選」）が
完全に一致したため、確定とする。本質は **「足し算を禁止し、引き算を強制する」**。

### 3-1. 揃える（3つ）
- **フォント1種**: 游ゴシック または メイリオが無難。装飾フォントは禁止。
- **配色は3カテゴリのみ**: ベース : メイン : アクセント = **70 : 25 : 5**。基本1色＋その濃淡。
- **図/イラストのテイストを統一**: 世界観（シンプル系など）を揃える。

### 3-2. 減らす（5つ）
- **色数を絞る**（上記配分を超えない）
- **罫線を目立たせない**（グレー、または無し）
- **装飾を最小化**（太字・斜体・下線・サイズ変更は「本当に強調したい1箇所」のみ）
- **矢印を主役にしない**（あくまで補助図形）
- **アイコン/イラストを多用しない**（必要な部分だけ）

### 3-3. 守る（構造・チャートの原則）
- **1スライド1メッセージ**（リード文＝言いたいことは2行で記入。サイズ・色は変えない／26則）
- **視線はZ型**（左上→右下）を基本に配置
- **時系列は左→右**に配置（縦並びは情報量が多いときのみ／26則）
- **画像は左に配置**（人は右脳でビジュアルを認識／26則）
- **数字は大きく、単位は小さく**（数字の訴求力を上げる／26則）
- **テキスト色は真っ黒を避ける**（パレット黒列上から3つ目相当のグレー／26則）→ Theme.ink で固定
- **4行以上のテキストは左揃え**（中央揃えは始点がばらつき読みにくい／26則）
- **円グラフは避ける**（人は角度の差を認知しにくい。比較は横棒で）
- **グラフはタイトル・メモリ・罫線を削除**（必要な情報だけを残す／26則）
- **ナンバリング・箇条書きは極力避ける**（オブジェクトの並列で表現／26則）
- 一番読みやすいのは「文字だけのスライド」と「表」。それで足りないときだけ別形式を使う。

### 3-4. 作成順序（土台→中身）
1. ルール確定（フォント・色・余白）
2. **Wordでアウトライン**を作る（PowerPointを開く前に論理を固める）
3. 型を選択
4. 流し込み

## 4. 型カタログ v0

スライド1枚の構成は「**要素数**」でほぼパターン化できる、という指針に基づく。
AIは「タイトル＋要素N個」を書けばよく、レイアウト選択はパーサー側が要素数から決める。

### 4-1. 報告・提案系（メッセージ駆動：言いたいこと→根拠）

| 型 | 用途 | 要素数の目安 | 表現 |
|---|---|---|---|
| エグゼクティブサマリー | 冒頭1枚で全体像 | 3〜4 | 文字＋数字強調 |
| 横並び比較 | Before/After、他社比較 | 2〜4 | 横棒・表 |
| イシューツリー | 課題分解 | 3〜7 | ツリー |
| プロセス/タイムライン | 手順・ロードマップ | 4〜6 | 矢印フロー |
| ファクト＋示唆 | データの意味づけ | 2段組 | グラフ＋テキスト |
| KPI/数値ハイライト | 実績報告 | 1〜4 | 大数字 |

### 4-2. 技術系（構造駆動：実体の関係をそのまま描く）

| 型 | 用途 | 要素数の目安 | 表現 |
|---|---|---|---|
| アーキテクチャ図 | システム構成 | 可変 | **Mermaid流用** |
| シーケンス/フロー | 処理の流れ | 可変 | **Mermaid流用** |
| レイヤー図 | 階層スタック | 3〜6 | 積層ボックス |
| 仕様テーブル | API・パラメータ | 可変 | 表 |

> 報告系は独自DSLを設計し、技術系の図は既に強い Mermaid を中間表現として流用する
> ハイブリッド構成とする。

---

## 5. 実装ロードマップ（MNP推奨手順に準拠）

MNPの教え「**まず良い表現型を作ってからAI化する**」に沿う。
良い見た目が出せない段階でpptx化やAI化をしても無駄、という原則。

1. **設計ドキュメント一本化** ← 本書（完了）
2. **DSL記法を1〜2型で試作**（まず「横並び比較」あたり。「タイトル＋要素N個」をどう書くか）
3. **HTMLで描画を再現**（pptxの前に、記法→きれいなスライドが成立するか検証）
4. **potx連携・pptx生成**（python-pptxでレイアウト継承・プレースホルダー流し込み）
5. **AI化**（システムプロンプト型 / API型 / Skill配布。最後に「魂」を載せる）
